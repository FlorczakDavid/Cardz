L’ATELIER / CONFIGURATION V1

Votre jeu.
Vos règles.

Les cartes sont dans des fichiers JSON. Les règles aussi. Modifiez-les, enregistrez-les, publiez-les : le jeu les relit à son prochain chargement. Aucune compilation.

Le jeu se joue autour d’un seul écran. Il n’y a ni compte, ni salle multijoueur à distance, ni serveur de données. Les questions publiées sur GitHub Pages sont publiques ; vos réponses personnelles n’ont pas leur place dans ces fichiers.

01. Publier sur GitHub Pages

  1. Décompressez le paquet et créez un dépôt public sur GitHub.
  2. Chargez le contenu du dossier cardz avec ses sous-dossiers. Le fichier index.html doit être à la racine du dépôt, avec config.json et .nojekyll.
  3. Dans Settings → Pages, choisissez Deploy from a branch, puis main et /(root). Enregistrez.
  4. Attendez la publication et ouvrez le lien affiché par GitHub.

Les chemins relatifs permettent aussi une adresse de projet comme utilisateur.github.io/cardz/. Documentation officielle GitHub Pages ↗

Pour essayer localement, servez ce dossier avec un serveur statique, par exemple le serveur HTTP intégré à Python, puis ouvrez son adresse localhost. Le double clic sur le HTML ne suffit pas : les navigateurs bloquent la lecture des JSON et des modules depuis file://.

Utilisez un éditeur de texte ou l’éditeur GitHub. Le JSON exige des guillemets doubles, aucune virgule après le dernier élément et aucun commentaire. Une erreur s’affiche dans le jeu, avec le champ ou le fichier concerné.

03. Ajuster les ratios

ratioStages contient une liste de plages. from et to sont inclusifs ; les plages commencent à 1 et se suivent sans trou ni chevauchement. weights associe un poids à chaque identifiant de type.

Ce tableau rappelle les valeurs initiales du document ; le jeu utilise toujours les valeurs actuelles de config.json.

{
  "from": 11,
  "to": 25,
  "weights": {
    "ouverture": 20,
    "intermediaire": 70,
    "deep": 10,
    "miam": 0
  }
}

Les poids sont relatifs : 2 et 8 donnent les mêmes chances que 20 et 80. Il faut un poids positif par plage pour chaque jeu. Les types absents du jeu ou épuisés sont retirés, puis les chances des autres types positifs sont recalculées. Un type à zéro ne peut pas sortir.

Le numéro augmente même quand une carte est passée. Après la dernière plage, game.afterLastStage vaut "repeat-last" : le dernier ratio continue. Utilisez "stop" pour arrêter. game.maxQuestions vaut null pour ne pas fixer d’autre limite, ou un entier pour en fixer une.

04. Créer un type de carte

  1. Ajoutez un objet dans categories avec un id unique, un label, un symbol, une color au format #RRGGBB et une description. Choisissez une couleur claire pour garder le texte sombre lisible.
  2. Ajoutez son identifiant dans categories des jeux qui doivent l’utiliser, dans decks.
  3. Donnez-lui un poids dans les plages où il peut sortir.
  4. Ajoutez des questions portant cet identifiant dans leur champ category.

Pour le couple, le PDF ne donne pas de ratio propre : les questions conservent la catégorie source couple et le tag couple. Le réglage categoryMappings.couple les envoie initialement vers deep. Vous pouvez les associer à un autre type existant. Pour créer un vrai type couple, retirez d’abord cet alias, puis déclarez le type, les jeux et ses poids.

05. Ajouter des questions sans toucher aux originales

Le paquet supplémentaire est une source distincte. Dans l’interface, cochez ce paquet dans « Les cartes à mettre dans la pioche » pour l’activer. Pour l’activer à chaque nouvelle ouverture, changez sources → source additional → defaultEnabled en true.

{
  "id": "ma-question-001",
  "category": "intermediaire",
  "text": "Votre question ici ?",
  "tags": [],
  "minPlayers": 2,
  "enabled": true
}

L’identifiant doit être unique dans tous les paquets, commencer par une lettre minuscule et ne contenir que lettres minuscules sans accent, chiffres, tirets ou traits de soulignement. maxPlayers est facultatif. Un tag présent dans excludedTags d’un jeu exclut la question de ce jeu.

Pour un troisième paquet, créez un fichier reprenant la structure des autres, puis ajoutez une entrée dans sources. Son champ origin doit correspondre à l’id de cette source. path reste un chemin relatif vers un JSON à l’intérieur du dossier du jeu. required: false permet de jouer si ce paquet est absent ; un paquet obligatoire invalide arrête le chargement.

Les 204 entrées originales comprennent trois formulations répétées, soit 201 formulations distinctes. Elles sont conservées dans le catalogue, mais pas répétées dans la partie par défaut. Les 20 propositions supplémentaires sont étiquetées comme ajouts et ne remplacent aucune question originale.

06. Changer le tour de parole

Réglage dans gameEffet

firstAsker"first" fait commencer le premier prénom ; "random" tire au sort la personne qui commence.
targetCountsSeuils croissants : minPlayers: 2, count: 1, puis minPlayers: 4, count: 2 par défaut. Chaque cible est distincte et ne pose pas la question.
allowAdditionalRespondersAutorise les autres personnes à se proposer.

noRepeatTextEmpêche deux entrées de même formulation d’apparaître dans une partie. Une même entrée ne repasse jamais.

Les textes de rules.items et rules.howTo modifient l’aide affichée. Les réglages de game modifient les comportements décrits ci-dessus. Écrire une nouvelle mécanique en prose ne suffit pas à l’exécuter : un comportement entièrement nouveau demanderait de modifier le moteur.

07. La capsule à deux

closure.enabled active ou désactive la capsule. prompt est la dernière question, delayDays le délai en jours, et maxAnswerLength la limite de caractères jusqu’à 12 000. La capsule reste réservée à deux personnes.

Chaque réponse est chiffrée avec sa phrase secrète. Les textes et phrases ne sont pas envoyés à un serveur. Le navigateur conserve le texte chiffré ; exporter la capsule crée une sauvegarde JSON que l’on peut importer ailleurs. Sans phrase secrète, aucune récupération n’est prévue.

Le délai utilise l’horloge de l’appareil. Sans serveur de confiance, on ne peut pas garantir qu’une personne déterminée attendra cinq jours. Le chiffrement protège les réponses sans la phrase secrète ; le calendrier reste une règle de jeu. Effacer les données du navigateur supprime les capsules non exportées.

Pour tester l’ouverture, créez une capsule dans une copie locale avec delayDays: 0. Changer le délai plus tard ne change pas une capsule existante : sa date fait partie des métadonnées authentifiées.

08. Vérifier avant de republier

  1. Gardez une copie des fichiers que vous allez modifier.
  2. Vérifiez le JSON dans un éditeur compatible et rechargez le jeu après chaque changement.
  3. Avec Node.js 20 ou plus, les commandes npm test et npm run check contrôlent les données et le moteur. Aucune installation npm n’est nécessaire.
  4. Après publication, testez une partie à deux, une partie à quatre, une carte passée, une reprise après actualisation et une capsule exportée puis importée.

Les prénoms et la progression sont stockés localement en clair ; les réponses des capsules sont chiffrées. Une modification des règles ou des cartes invalide la progression enregistrée. Les capsules restent indépendantes. Le jeu n’ajoute pas de service worker susceptible de garder d’anciennes règles.
